# ruEncod — специализированный токенизатор для русского языка

Дата: 2026-10-12
Статус: на ревью

## 1. Цель и критерии успеха

**Зачем.** Обучить токенизатор, оптимизированный под русский язык, для будущей языковой модели
размером ~1B+ параметров, обучаемой с нуля. Попутно получить материалы для Telegram-поста о том,
как нейросеть «видит» текст и почему русский в существующих LLM обходится дороже английского.

**Важная оговорка (войдёт в пост).** Собственный токенизатор не удешевляет API GPT/Claude — они
тарифицируют по своим токенизаторам. Экономия реальна только для модели, обученной на нашем
токенизаторе. В посте считаем «сколько стоил бы тот же текст при той же цене за токен».

**Критерии успеха:**
1. Финальный токенизатор даёт заметно меньше токенов на слово русского текста, чем o200k (GPT-4o)
   и Claude, на всех русских доменах отложенной выборки.
2. Английский и код не деградируют катастрофически (измеряем, порог не фиксируем — это компромисс).
3. Ровно-обратимость: `decode(encode(x)) == x` для 100% отложенной выборки.
4. Есть обоснованный выбор алгоритма и размера словаря: кривые сжатия + проверка на мини-LM (этап 6).
5. Готовы: графики, картинки разбиения, интерактивная страница, черновик поста — на реальных цифрах.

**Вне рамок:** обучение самой 1B-модели; GPU-эксперименты; токенизация не-русских языков кроме
английского/кода.

## 2. Принятые решения

| Вопрос | Решение |
|---|---|
| Назначение | Основа для модели ~1B+ с нуля + материалы для поста |
| Корпус | Все домены, ~5 ГБ, сбалансированно |
| Алфавит | Русский + минимальная латиница/цифры/код (~5% корпуса) |
| Буква ё | Не трогаем. Нормализация только NFC |
| Алгоритмы | BPE vs Unigram vs morph-BPE |
| Морфология | Вариант A (MorphBPE-подобный): запрет слияний через границы морфем только при обучении |
| Размеры словаря | 16k / 32k / 48k / 64k / 96k |
| Сравнение | o200k, cl100k, Llama 3, Qwen 3, Mistral, Gemma 3, ruGPT-3, Vikhr; Claude через `count_tokens` |
| Цифры | Разбиваются поштучно |
| Мини-LM проверка | Да, этап 6 |

## 3. Окружение

- Python 3.12 через `uv` (системный 3.14 — риск отсутствия колёс у `tokenizers`/`torch`).
- Основные зависимости: `tokenizers`, `datasets`, `huggingface_hub`, `pymorphy3`, `regex`,
  `tiktoken`, `transformers` (только для загрузки baseline-токенизаторов), `anthropic`,
  `torch` (CPU), `matplotlib`, `pandas`, `pyyaml`, `pytest`.
- Железо: 20 ядер CPU, ~10 ГБ свободной RAM, без GPU. Все этапы рассчитаны на CPU.

## 5. Этап 1 — Данные

### 5.1 Источники и доли

| Домен | Доля | Источник (HF Hub) |
|---|---|---|
| web | 30% | `HuggingFaceFW/fineweb-2`, конфиг `rus_Cyrl` |
| wiki | 15% | `wikimedia/wikipedia`, русский дамп |
| social | 15% | Pikabu (`IlyaGusev/pikabu`) + диалоги/комментарии |
| it | 10% | Хабр (`IlyaGusev/habr`) |
| books | 10% | Викитека (public domain) |
| news | 10% | `IlyaGusev/gazeta` + новостная часть FineWeb-2 |
| niche | 5% | Право (RusLawOD или аналог), медицина (открытые корпуса) |
| en_code | 5% | `HuggingFaceFW/fineweb-edu` (сэмпл) + `bigcode/the-stack-smol` |

Доли — в байтах. Точные идентификаторы наборов для social/books/niche проверяются при реализации;
если источник недоступен — подбирается замена, фиксируется в `experiments.yaml`, о замене
сообщается пользователю. Загрузка — потоково (`streaming=True`), до набора байтового бюджета домена.

### 5.2 Очистка

По порядку: NFC → удаление HTML-тегов/сущностей → схлопывание мусорных повторов пробелов
**не делаем** (пробелы — часть текста, обратимость) → фильтр длины (от 200 символов до 100 тыс.;
длинные режутся по абзацам) → для русских доменов фильтр доли кириллицы среди букв ≥ 0.6 →
точная дедупликация по хешу нормализованного текста (в пределах всего корпуса).

### 5.3 Разделение

До обучения из каждого домена откладывается `heldout` ≈ 50 МБ (по документам, случайно,
фиксированный seed). Heldout не используется ни на каком этапе обучения — ни токенизаторов,
ни мини-LM.

Формат хранения: `data/clean/<domain>/*.jsonl.zst` (`{"text": ..., "domain": ...}`).

### 5.4 Морфологические данные

- Источник: морфемно-орфографический словарь Тихонова (~100k лемм с разметкой
  приставка/корень/суффикс/окончание/постфикс) — из открытых репозиториев исследований морфемной
  сегментации (напр., данные Сорокина и Кравцовой).
- Делим леммы 90/10 (seed): **train** — для ограничений при обучении morph-BPE,
  **test** — только для оценки морфемного F1. Тестовые леммы и все их словоформы не получают
  морфологических ограничений при обучении.

**Перенос разбора на словоформы** (`morph/project.py`):
1. `pymorphy3` разбирает словоформу → нормальная форма (лемма) и лексема (все формы).
2. Поиск леммы в словаре — в нижнем регистре, `ё→е` только для сопоставления.
3. Основа лексемы = наибольший общий префикс всех её форм.
4. Границы морфем леммы, лежащие внутри основы, переносятся на словоформу.
5. Граница основы/окончания: после основы. Если форма заканчивается на `ся`/`сь` и это постфикс
   (по разбору леммы), он отделяется.
6. Остаток между основой и постфиксом — одним куском (сознательное упрощение).
7. Регистр исходного слова сохраняется (смещения по символам).
8. Нет в словаре / неоднозначно не разобралось → слово без ограничений.

Пример: «переписывать» → `пере|пис|ыва|ть`; «книгами» → `книг|ами`.

Сохраняется кэш `data/morph/segmentations.tsv` для всех уникальных слов корпуса с частотой ≥ 5
(слова реже — без ограничений). Метрика покрытия: доля словоупотреблений русского корпуса,
получивших сегментацию — пишется в лог и в `results/`.

## 6. Этап 2 — Обучение токенизаторов

### 6.1 Общая предобработка (одинакова для всех вариантов)

- **Нормализатор:** NFC.
- **Предтокенизатор** (`pretok.py`): регулярка в стиле o200k (`\p{L}`-классы, работает для
  кириллицы), но цифры — по одной (`\p{N}` по одному символу), затем ByteLevel
  (`add_prefix_space=False`).
- **Спецтокены:** `<|bos|>`, `<|eos|>`, `<|pad|>`, `<|im_start|>`, `<|im_end|>`, плюс
  `<|reserved_0|>`…`<|reserved_250|>` — всего 256. Входят в заявленный размер словаря.
- Начальный алфавит: все 256 байтов → нет UNK.

### 6.2 Единый конвейер обучения

Чтобы варианты отличались **только** алгоритмом/ограничениями:
1. `morph/segment_corpus.py` прогоняет обучающий корпус через `pretok.py` и пишет
   «сегментированный» корпус: все предтокены разделены служебным символом `U+E000`.
   Для варианта morph-bpe дополнительно ставится `U+E000` на границах морфем (из кэша 5.4).
   Пробел, прилипший к началу слова, остаётся с первой морфемой.
2. Тренер получает предтокенизатор `Split("", removed) → ByteLevel(use_regex=False)`,
   т.е. сливает только внутри кусков.
3. После обучения предтокенизатор в `tokenizer.json` заменяется на стандартный из 6.1.
   Итог — обычный HF `tokenizer.json`, загружается `transformers` и `transformers.js`.

Получаем два сегментированных корпуса: `plain` (для bpe и unigram) и `morph` (для morph-bpe).

### 6.3 Варианты

| Имя | Тренер | Корпус |
|---|---|---|
| `bpe-{V}` | HF `BpeTrainer` | plain |
| `unigram-{V}` | HF `UnigramTrainer` | plain (сэмпл, см. ниже) |
| `morph-bpe-{V}` | HF `BpeTrainer` | morph |

`V ∈ {16k, 32k, 48k, 64k, 96k}` → 15 токенизаторов.

Unigram обучается через HF `UnigramTrainer` (а не sentencepiece), чтобы предтокенизация была
идентичной BPE — иначе сравнение нечестное. Из-за памяти Unigram обучается на сэмпле ~1.5 ГБ
сегментированного корпуса с теми же долями доменов. Если HF Unigram не помещается в RAM даже так —
запасной вариант: sentencepiece Unigram (`byte_fallback`, `split_digits`,
`remove_extra_whitespaces=False`, `normalization_rule_name=identity`) с явной пометкой в
результатах о другой предтокенизации.

Детерминизм: фиксированный порядок данных и seed; проверяется тестом (6.5).

### 6.4 Ожидания по ресурсам

BPE: минуты на модель. Unigram: десятки минут. Вся сетка — один «ночной» прогон.

## 7. Этап 3 — Оценка

### 7.1 Метрики (на heldout, по каждому домену и суммарно)

- **fertility** — токенов на слово (слово = последовательность `\p{L}+` по регулярке);
- **chars/token**, **bytes/token**;
- **% слов в 1 токен**;
- **использование словаря** — доля словаря, встретившаяся в heldout;
- **морфемный F1** — точность/полнота/F1 границ токенов относительно границ морфем на
  test-леммах и их словоформах (слова кодируются с ведущим пробелом, как в тексте);
- **обратимость** — доля документов с `decode(encode(x)) == x` (ожидается 100%).

### 7.2 Baseline-токенизаторы

Офлайн: o200k и cl100k (`tiktoken`), Llama 3, Qwen 3, Mistral, Gemma 3, ruGPT-3, Vikhr
(`transformers.AutoTokenizer`; для gated-моделей — открытые зеркала токенизаторов или
`huggingface-cli login`). Те же метрики, кроме морфемного F1 (считаем и для них — это интересно
для поста).

Claude: `client.messages.count_tokens` на сэмпле ~200 документов на домен, ключ из
`ANTHROPIC_API_KEY`. Модель — актуальная модель Claude на момент реализации. Вычитаются
служебные токены обёртки сообщения (замеряются на пустом/односимвольном сообщении). Ответы
кэшируются на диск, чтобы не дёргать API повторно.

### 7.3 Деньги

Стоимость 1000 слов русского текста = fertility × 1000 × цена за входной токен для GPT-4o/
актуальной GPT и Claude. Для нашего токенизатора — «при той же цене за токен». Цены берутся из
официальной документации на момент реализации и фиксируются в `experiments.yaml` с датой.

### 7.4 Вывод

`results/metrics.csv`: одна строка = (tokenizer, domain, metric, value). Все графики и пост строятся
только из этого файла (и `lm_bpb.csv`).

## 8. Этап 6 — Проверка на мини-LM

**Вопрос:** даёт ли лучшее сжатие лучшую модель? Сравниваем алгоритмы при **одинаковом размере
словаря** — выбранном по кривым этапа 3 (ожидается 48k или 64k).

- **Кандидаты:** `bpe-V`, `unigram-V`, `morph-bpe-V`; плюс o200k как внешний ориентир.
- **Модель:** decoder-only трансформер (GPT-2-подобный, RoPE, связанные эмбеддинги),
  d=384, 6 слоёв, 6 голов, контекст 512 → ~10.6M параметров без эмбеддингов. Одинакова для всех
  кандидатов (отличается только матрица эмбеддингов).
- **Данные:** одинаковый **байтовый** бюджет обучающего текста для всех кандидатов
  (по умолчанию 100 МБ, параметр в конфиге), один и тот же срез обучающего корпуса.
  Токенизаторы со сжатием лучше получают меньше токенов — это честно.
- **Обучение:** AdamW, cosine schedule, одинаковые гиперпараметры, 1 эпоха, seed фиксирован.
  CPU, `torch.set_num_threads(20)`.
- **Метрика:** bits-per-byte на heldout по доменам:
  `bpb = Σ NLL(nats) / ln 2 / Σ bytes(utf-8)`. Не зависит от токенизатора — сравнимо.
- **Время:** ориентир несколько часов на кандидата → ночной прогон; бюджет регулируется в конфиге.
  Перед полным прогоном — короткий smoke-run (1 МБ) для оценки скорости.
- **Ограничение:** один seed, маленькая модель → результат индикативный, разница < ~1% bpb
  считается шумом и так и формулируется в посте.

Результат: `results/lm_bpb.csv`.

## 9. Выбор финалиста

Правило: среди вариантов размера V берём минимальный bpb (этап 6); при разнице в пределах шума —
лучший по fertility на русских доменах. Размер V обосновывается кривой «размер словаря → сжатие»
(точка, после которой прирост сжатия < ~2% на удвоение словаря) с учётом того, что для 1B-модели
словарь 48–64k не раздувает долю эмбеддингов. Финалист копируется в `artifacts/final/` и
коммитится.

- **Графики** (`viz/charts.py` → `results/figures/*.png`, единый стиль, читаемы на телефоне):

  2. кривая «размер словаря → fertility» для bpe/unigram/morph-bpe;
  3. fertility по доменам (наш финалист vs o200k vs Claude);
  4. стоимость 1000 слов, $;
  5. bpb мини-LM по кандидатам.
- **Картинки разбиения** (`viz/splits.py`): 6–8 примеров — «достопримечательностями»,
  «переподготовка», «нейросеть», число «1234567», фраза со смешанным английским, короткое
  предложение. Строки: GPT-4o, Llama 3, наш bpe, наш morph-bpe (цветные плашки токенов);

- **Интерактивная страница** (`web/index.html`): поле ввода → разбиение и счёт токенов

  ссылкой — решение пользователя.
- **Черновик поста** (`post/draft.md`): как нейросеть видит текст → почему русский дороже →
  эксперимент → цифры → оговорка про API → ссылка на страницу. Все числа — из `metrics.csv`/
  `lm_bpb.csv`.

## 11. Тестирование

`pytest`, быстрые тесты на крошечных фикстурах (без скачивания данных):
- обратимость encode/decode на разнообразных строках (кириллица, ё, эмодзи, код, пробелы, табы,
  переводы строк, смешанный регистр);
- цифры кодируются поштучно;
- все 256 спецтокенов на месте и атомарны;
- замена предтокенизатора после обучения (6.2) не ломает кодирование (сравнение с ожидаемыми
  токенами на мини-корпусе);
- `project.py`: `переписывать → пере|пис|ыва|ть`, `книгами → книг|ами`, регистр сохраняется,
  слово вне словаря → без ограничений;
- morph-bpe на мини-корпусе не содержит в словаре токенов, пересекающих размеченные границы;
- метрики: fertility, F1 границ, bpb — против посчитанных вручную значений;
- детерминизм: два обучения на мини-корпусе дают идентичный `tokenizer.json`.

## 12. Риски

| Риск | Митигация |
|---|---|
| Набор данных недоступен/gated | Замена из конфига, сообщить пользователю |
| Unigram не помещается в RAM | Меньший сэмпл → запасной sentencepiece с пометкой |
| Низкое покрытие словарём Тихонова | Метрика покрытия в отчёте; ограничения работают на частотной части |
| Мини-LM слишком медленная на CPU | Smoke-run, уменьшение байтового бюджета |
| Baseline-токенизаторы gated (Llama, Gemma) | Открытые зеркала токенизаторов или HF login |
| Изменение цен API | Цены фиксируются с датой в конфиге |
